# 新規環境の構築手順(T-18)

新しい顧客(メディア運営者)を迎えるたびに、この手順で環境を1つ作る。
**1環境 = 1顧客 = 1 Xserver契約**(CLAUDE.md 1章)。

前提として [Xserver実機調査手順](Xserver実機調査.md) が完了し、
[SPEC.md 13.1](../SPEC.md#131-共有レンタルサーバーの制約と対処) の「要確認事項」が
確定していること。特に `symlink()` の可否によって手順が変わる(2章を参照)。

---

## 0. Xserver 側の準備(サーバーパネル)

| 項目 | 操作 |
|---|---|
| ドメイン | 顧客のドメインを追加(独自ドメイン、または `xxx.xsrv.jp` のサブドメイン) |
| SSL | 「独自SSL設定」で無料独自SSLを有効化。反映まで数十分かかることがある |
| PHP バージョン | 「PHP Ver.切替」で対象ドメインを **PHP 8.4** に変更(新規ドメインの初期値は 8.3) |
| データベース | MySQL 8.0 のデータベースを 1 つ作成。ユーザーも作成し、権限を付与する |
| SSH | 有効化し、公開鍵を登録する |

---

## 1. ディレクトリ構成を作る

[SPEC.md 13.2](../SPEC.md#132-環境構成) の構成に従う。Laravel 本体を公開領域の外に置き、
`public_html` を `app/public` へのシンボリックリンクに置き換える。

```
/home/[アカウント]/
  app/                          ← Laravel 本体(Web から見えない)
    .env
    public/
  [顧客のドメイン]/
    public_html  → symlink →  /home/[アカウント]/app/public
```

```bash
# SSH で接続して実行する
cd ~
git clone <リポジトリURL> app
cd app

# 既存の public_html を退避してからシンボリックリンクに置き換える
mv ~/顧客のドメイン/public_html ~/顧客のドメイン/public_html.bak
ln -s ~/app/public ~/顧客のドメイン/public_html
```

### 1.1 `symlink()` が使えない場合(要確認事項でNGだった場合)

Xserver実機調査で `symlink()` が使えないと判明していたら、上記は使えない。
代わりに Laravel 本体を `public_html` の**外**(例: `~/app`)に置くのは同じだが、
リンクではなく `public_html` の中身を Laravel の `public/` の内容で直接構成し、
`index.php` の `require` パスだけを絶対パスで書き換える方式に切り替える。

```bash
cp -r ~/app/public/* ~/顧客のドメイン/public_html/
```

`public_html/index.php` 内の `require __DIR__.'/../vendor/autoload.php'` 等を
`~/app/vendor/autoload.php` のような絶対パスに書き換える。この場合、
`public/build`(フロントのビルド成果物)や `storage/app/public` へのシンボリックリンクも
同様に手動コピーへ切り替える必要があることに注意する。

**この方式は `deploy.sh` の `git pull` だけでは `public_html` に反映されないため、
デプロイ手順にコピー処理を追加する必要がある。** 採用した場合は
[デプロイ手順.md](デプロイ手順.md) にその旨を追記すること。

## 2. アプリケーションの設定

```bash
cd ~/app

# 依存関係(本番用。開発ツールは入れない)
composer install --no-dev --optimize-autoloader

# .env を作成し、顧客ごとの値を設定する
cp .env.example .env
php artisan key:generate --force
```

`.env` で必ず確認・設定する項目:

| 項目 | 値 |
|---|---|
| `APP_ENV` | `production` |
| `APP_DEBUG` | **`false`**(エラー詳細を外部に晒さない) |
| `APP_URL` | `https://顧客のドメイン` |
| `DB_*` | 手順 0 で作成した MySQL の接続情報 |
| `QUEUE_CONNECTION` | `database`(常駐ワーカーが使えないため。CLAUDE.md 4章) |
| `SESSION_DRIVER` / `CACHE_STORE` | `database`(Redis が無いため) |
| `MAIL_*` | 外部 SMTP(SendGrid / SES)の接続情報。mailpit は本番で使わない |
| `FILESYSTEM_DISK` | `local`(既定のままでよい。画像は `uploads` ディスク固定) |

```bash
# マイグレーションと初期マスタの投入
php artisan migrate --force
php artisan db:seed --force

# public/build はリポジトリに含まれているため、git clone の時点で揃っている。
# 本番で npm run build は実行しない(Node.js が無い。CLAUDE.md 4章)。

# uploads ディスクの書き込み確認(画像アップロードの保存先。CLAUDE.md 3.10)
php artisan tinker --execute="\Illuminate\Support\Facades\Storage::disk('uploads')->put('healthcheck.txt', 'ok');"
```

## 3. cron の登録(サーバーパネルの「Cron設定」から)

| 実行間隔 | コマンド |
|---|---|
| 毎分 | `php ~/app/artisan schedule:run` |
| 毎分 | `php ~/app/artisan queue:work --stop-when-empty --max-time=50` |
| 毎日 1 回(深夜帯) | `~/app/backup.sh` |

`schedule:run` が呼び出すバッチ(掲載期限切れ処理・アグリゲーションフィード生成)は
`routes/console.php` に登録済みで、追加の cron 登録は不要。

**cron の最小間隔が 1 分でない環境の場合**、キューの遅延・スケジューラの実行間隔が
仕様より延びる。[Xserver実機調査手順](Xserver実機調査.md) の確認結果に応じて
通知の遅延に関する案内文言を調整すること。

## 4. 動作確認(完了条件)

- `https://顧客のドメイン/` にアクセスしてトップページが表示される
- HTTPS で接続され、証明書の警告が出ない
- **`https://顧客のドメイン/.env` にアクセスして 404 になることを確認する**
  (200 や 500 が返る場合はディレクトリ構成が誤っている。即座に見直す)
- 運営者アカウントでログインでき、サイト設定・マスタ管理画面が開ける
  (運営者アカウントの作成は `php artisan tinker` で `AdminUser::create()` するか、
  専用のシーダー/コマンドを別途用意する)
- cron 登録から数分待ち、`storage/logs/laravel.log` にスケジューラ実行のエラーが
  出ていないことを確認する
